# AGENTS.md — MTS Marketolog SMS Templates Optimus

## 1. Назначение проекта

Десктопное приложение для анализа SMS-шаблонов, отправленных через агрегатор МТС-Маркетолог.

Задачи:

1. Импортировать стандартную Excel-выгрузку статистики отправок из личного кабинета МТС-Маркетолог.
2. Импортировать Excel-список активных SMS-шаблонов.
3. Показывать по каждому шаблону: активность, процент срабатывания, количество сообщений и SMS-сегментов, фактическую стоимость, экономическую выгоду.
4. Автоматически находить группы однотипных незашаблонированных сообщений, генерировать шаблон-кандидат и считать выгоду от его регистрации.
5. Моделировать разные модели тарификации (пакетную, подписочную, оплату по факту), чтобы корректно считать выгоду.

Ограничения:

- Работа только с локальными выгрузками. Приложение не должно ходить в API МТС-Маркетолога без отдельного решения.
- Исходные файлы в `doc/` — только чтение. Не изменять и не удалять.
- Реальные выгрузки содержат персональные данные. В репозиторий их не коммитить.

### Критичные особенности данных

1. **Дубликаты `ID сообщения` — это не случайные повторы.** Одна и та же отправка может быть представлена несколькими строками с разными `Тип пакета` / `Цена за один сегмент` / `Стоимость`. Это биллинговые компоненты. Для логического сообщения:
   - считать сообщение один раз по `ID сообщения`;
   - суммировать `Стоимость` по всем строкам ID;
   - суммировать `Количество сегментов в sms` по строкам: длинная SMS оплачивается несколькими частями (например, 23 + 5 + 15 = 43 сегмента);
   - проверять совпадение текста, номера и времени; расхождения — в отчёт о качестве.
   В известных данных у части дубликатов различается количество сегментов (октябрь — 2 887 ID, ноябрь — 404 ID). Это не повод отбрасывать строки: стоимость и сегменты суммируем, расхождение показываем. Сумма сегментов по строкам совпадает с ЛК МТС-Маркетолога (октябрь: обычные 61 986, шаблонированные 140 911).
2. **Нулевая стоимость — норма.** В подписке сообщение внутри оплаченного блока имеет `Стоимость = 0`, а `Цена за один сегмент` показывает ставку блока. Нельзя восстанавливать стоимость как `цена × сегменты`.
3. **Пустой `Тип пакета` / `Цена за один сегмент`** — ошибка отправки, обычно «Нет подходящего пакета SMS». Такие строки исключать из экономики, но показывать в отчёте.
4. **`Количество sms в пакете при покупке = 999999999`** — сентинел для подписки, не реальный размер пакета.
5. **Ноябрь — неполный месяц** (по 16.11.2026). Не сравнивать абсолютные суммы с октябрём без нормализации или явного предупреждения.
6. **Октябрьские ставки обычной подписки** в данных: 33 / 42 / 8 ₽. В прайсе на 01.11.2026: 33 / 52 / 8,5 ₽. Значит, исторические периоды нужно считать по ставкам периода, а не по текущему прайсу.
7. **Названия операторов** в выгрузке: `MTS`, `Tele2`, `Megafon`, `Beeline`, `Other_RF`, `Rostelecom`, `Sbertelecom`, `Smarts_motiv`, `International`, пустая строка. Приложение не должно падать на неизвестном операторе — нужен fallback и предупреждение.
8. **Статусы отправки и доставки — разные.** `Отправлено` ≠ `Успешная доставка`. Считать нужно оба.

| Слой | Решение |
|---|---|
| Язык | Python 3.12 |
| Пакетный менеджер | `uv` |
| ETL больших Excel | `polars` + `fastexcel`; `openpyxl` для отчётов и небольших файлов |

| БД | SQLite через stdlib `sqlite3`, WAL, явные индексы |
| Конфиг | TOML, чтение через stdlib `tomllib` |
| UI | PySide6 (Qt for Python), отдельный слой `presentation` |
| Тесты | `pytest`, `pytest-cov` |
| Качество | `ruff` (lint + format), `mypy` |
| Деньги | `decimal.Decimal`, никогда `float` |
| Архитектура | Domain-Driven Design + чистая архитектура (раздел 5) |

Правила зависимостей:

- Домен не зависит от инфраструктуры; зависимости направлены внутрь.
- Не добавлять новую библиотеку, если хватает stdlib и уже выбранного стека.
- Не использовать `pandas` без доказанной необходимости: для больших таблиц есть `polars`.
- Не использовать ORM: SQLite-схема небольшая, SQL прозрачнее.
- Не делать сетевых вызовов из домена и приложения.

## 5. Архитектура и DDD

Проект следует принципам Domain-Driven Design в объёме, соразмерном задаче:
модель предметной области первична, инфраструктура вторична, единый язык
проходит через код, тесты, UI и документацию.

Чистая архитектура, зависимости направлены внутрь:

```text
presentation  ->  application  ->  domain
      |                 |
      +------ infrastructure (реализует порты)
```

- `domain` — сущности, value objects, тарифные модели, расчёт выгоды, матчинг и сигнатурная группировка. Не импортирует `application`, `infrastructure`, `presentation`, Qt, SQLite, Excel.
- `application` — use cases и порты (интерфейсы репозиториев/ридеров). Оркестрирует домен, не знает про Qt и SQLite.
- `infrastructure` — Excel-адаптеры, SQLite-репозитории, TOML-каталог тарифов, логирование.
- `presentation` — PySide6 UI, view models, диалоги. Работает только через application use cases/DTO.
- `composition.py` — единственное место сборки зависимостей.

### 5.1 Ограниченные контексты (bounded contexts)

Модель разделена на контексты. Границы контекстов — это границы смысла: термин
в разных контекстах может значить разное, и это нормально.

| Контекст | Ответственность | Пакеты |
|---|---|---|
| Импорт выгрузок | чтение Excel, нормализация, схлопывание биллинговых строк, качество данных | `domain/analytics/import_aggregation.py`, `application/use_cases/import_statistics.py`, `infrastructure/excel/` |
| Тарификация | тарифные модели, стоимость, наблюдаемые ставки, каталог | `domain/tariffs/`, `infrastructure/tariffs/` |
| Анализ шаблонов | матчинг, активность, выгода, сигнатурная группировка, кандидаты | `domain/analytics/` |
| Представление | экраны, view models, форматирование, экспорт | `presentation/`, `application/use_cases/export_report.py` |

Правила контекстов:

- Контексты — логические модули в одном процессе и одной БД. Микросервисы,
  отдельные БД и синхронизация между контекстами не вводятся.
- Контекст не импортирует внутренности другого контекста напрямую: обмен идёт
  через доменные типы (`SmsMessage`, `SmsTemplate`, `TariffPlan`) или DTO
  приложения.
- Общая терминология (`Money`, `Operator`, `MessageClass`, `Period`) —
  разделяемый каркас, а не отдельный контекст.

### 5.2 Единый язык (ubiquitous language)

Один термин — одно имя в коде, тестах, UI и отчётах. Переименование «по вкусу»
запрещено: сначала меняется глоссарий, затем код.

| Понятие | Код | Комментарий |
|---|---|---|
| Сообщение (логическая отправка) | `SmsMessage` | один `ID сообщения`; не путать со строкой выгрузки |
| Биллинговая строка | `BillingRow` | часть агрегата `SmsMessage`, собственной идентичности не имеет |
| Шаблон | `SmsTemplate` | зарегистрированный шаблон, а не текст-кандидат |
| Запись шаблона | `registration` | строка выгрузки: `ID шаблона`, текст, операторы, статус; несколько записей с точным совпадением текста — один `SmsTemplate` |
| Кандидат | `CandidateGroup` | группа сообщений, ещё не ставшая шаблоном |
| Сегмент SMS | `segments` / `count_segments` | количество SMS-сегментов, целое ≥ 0 |
| Класс сообщения | `MessageClass` | `ORDINARY` / `TEMPLATED` |
| Оператор | `Operator` | нормализованный оператор выгрузки |
| Деньги | `Money` | `Decimal` в рублях |
| Период | `Period` | интервал с часовым поясом |
| Тариф | `TariffPlan` | пакет, подписка или оплата по факту |
| Стоимость | `cost` | фактическое списание из выгрузки |
| Базовая стоимость | `baseline_cost` | сколько стоило бы обычными SMS |
| Оценка по шаблону | `templated_cost` | средняя стоимость сегмента шаблонированных SMS × сегменты группы |
| Выгода | `net_benefit` | `baseline_cost − actual_cost` |
| Покрытие | `coverage` | доля сообщений отправителя, сопоставленных шаблону |
| Подпадание под шаблон | `matched_messages` | сообщение совпало с шаблоном по тексту и отправителю |
| Срабатывание | `triggered_messages` | подпало под шаблон и оплачено как шаблонированное |
| Процент срабатывания | `trigger_rate` | `triggered_messages / matched_messages` |
| Разбивка по операторам | `operator_triggers` / `OperatorTrigger` | подпало/сработало и сегменты подпавших для пары «шаблон, оператор получателя» |
| Доля шаблона во всех сегментах | `share_of_all_segments` | `matched_segments / AnalysisView.total_segments` за период |
| Доля шаблона в шаблонированных сегментах | `share_of_templated_segments` | `matched_segments / AnalysisView.templated_segments` за период |
| Загрузка / партия | `ImportBatch` | один импортированный файл |
| Прогон анализа | `AnalysisRun` | расчёт по `batch_id + config_hash` |
| Абонент | `subscriber` / `SegmentationStatistics.subscribers` | уникальный номер получателя с отправленными сегментами; нулевые (ошибка отправки) не входят |
| Оператор абонента | `SubscriberOperatorShare` | оператор, по которому у абонента больше всего сообщений; ничья — первый по алфавиту |
| Сегменты дня | `DaySegments` | SMS-сегменты календарного дня: всего по загрузке или подпавшие под шаблон |
| Распределение по сегментам | `SegmentCountBucket` | сколько абонентов или сообщений приходится на N SMS-сегментов; доля — от общего числа |
| Сообщение шаблона | `MatchedMessageView` | реальная отправка выгрузки, показанная в окне шаблона/кандидата; номер замаскирован |
| Статус отправки / доставки | `send_status` / `delivery_status` | исходные статусы логического сообщения из выгрузки |
| Тема оформления | `Theme` | палитра и QSS; идентификатор хранится в настройках как `theme` |

Правила языка:

- В коде — английские имена из колонки «Код»; в UI и отчётах — русские
  подписи из колонки «Понятие».
- Новое понятие добавляется в глоссарий в том же изменении, где появляется в коде.
- «Сообщение», «SMS-сегмент» и «строка выгрузки» никогда не называются одинаково.

### 5.3 Агрегаты и инварианты

Агрегат — граница согласованности и транзакции. Изменять агрегат можно только
через его корень, инварианты проверяются в конструкторе корня или доменного
сервиса-фабрики.

| Корень агрегата | Состав | Инварианты |
|---|---|---|
| `SmsMessage` | `BillingRow[]` | один `ID сообщения`; стоимость = сумма строк; сегменты = сумма строк; дата timezone-aware; текст и получатель не пустые |
| `SmsTemplate` | — | непустой текст; `template_id` уникален; `monthly_fee >= 0` |
| `AnalysisRun` | `TemplateMetrics[]`, `CandidateGroup[]` | метрики только для своего `batch_id`; ключ `batch_id + config_hash` уникален; выгода пересчитывается целиком |

Правила агрегатов:

- Один агрегат — одна транзакция. Межагрегатная согласованность — через
  application-сервис, без распределённых транзакций.
- Ссылки между агрегатами — только по идентификатору (`message_id`,
  `template_id`, `run_id`), не по объектной ссылке.
- `ImportBatch` — техническая запись контекста импорта: живёт в application DTO
  и SQLite, в доменную модель не проникает.
- Сборка агрегата из внешних строк — доменная фабрика
  (`aggregate_rows`), а не конструктор адаптера.

### 5.4 Доменные сервисы

Логика, которая не принадлежит одному агрегату, выносится в доменный сервис в
`domain/analytics/` или `domain/tariffs/` и принимает доменные типы:

- `matching` — сопоставление сообщения с шаблоном;
- `activity` / `benefit` — покрытие и экономическая выгода;
- `csg` — кандидаты: сигнатурная группировка, эмиссия и слияние литеральных участков;
- `calculator` / `observed` — расчёт стоимости и извлечение наблюдаемых ставок.

Сервис не работает с Qt, SQLite, Excel и не логирует. Ввод-вывод — забота
адаптеров.

### 5.5 Порты, репозитории, anti-corruption

- Порты объявляются как `typing.Protocol` в `application/ports.py`, реализации —
  в `infrastructure/`, подстановка — в `composition.py`.
- Репозиторий существует только для корня агрегата. Репозиториев «на каждый
  запрос» и «универсальных DAO» не делаем.
- Сознательное отклонение от канонического DDD: интерфейсы репозиториев лежат в
  `application`, а не в `domain`. Причина — домен не должен знать о
  персистентности вообще, а направление зависимостей то же. Решение фиксируется
  здесь, а не переизобретается в каждом модуле.
- Excel, TOML и SQLite — внешние модели. Их приводит к домену
  anti-corruption-адаптер: `ExcelStatisticsReader` отдаёт `RawSmsRow`, домен не
  знает названий колонок и типов ячеек.

### 5.6 Что сознательно не применяем

DDD-каркас без потребности — тоже долг. Не вводим, пока не появится второй
реальный сценарий:

- доменные события и шину событий — процесс один, вызовы синхронные;
- CQRS, event sourcing, sagas;
- отдельные БД и сервисы на каждый контекст;
- «инфраструктурные» абстракции ради симметрии (Unit of Work, generic repository);
- value object для одного числа без поведения (количество сегментов).

Правила:

- Бизнес-логика — только во внутренних слоях. UI не считает деньги и не парсит Excel.
- Домен не зависит от формата Excel: адаптер приводит файл к доменным строкам
  `RawSmsRow`, доменная фабрика `aggregate_rows` собирает из них агрегаты.
- Порты — `typing.Protocol`, реализации подставляются в composition root.
- Ошибки домена — собственные исключения (`DomainError`, `TariffError`, `StatisticsImportError`), не голые `Exception`.
- Не проглатывать ошибки. Пользователю — понятное сообщение, в лог — контекст без PII.
- Примитивы (`str`, `int`, `Decimal`) не пересекают границу домена, если у
  понятия есть правила: деньги, оператор, класс сообщения и период живут только
  как `Money`, `Operator`, `MessageClass`, `Period`. Исключения — идентификаторы,
  текст сообщения и количество сегментов (см. раздел 6).
- Новое поведение сначала моделируется в домене (сущность, value object или
  доменный сервис), и только потом появляется вызов в application или UI.
- Инфраструктурные детали (SQL, имена колонок Excel, TOML-ключи) не попадают в
  домен даже как строковые константы.

## 6. Доменная модель

### Сущности, агрегаты и value objects

Корни агрегатов помечены **(AR)**; их изменение и сохранение идут только через
корень.

- **(AR) `SmsMessage`** — логическая отправка: ID, дата, получатель, оператор, имя отправителя, текст, сегменты, статусы отправки и доставки, стоимость, тип пакета, биллинговые строки. Внутри агрегата — `BillingRow[]`.
- **(AR) `SmsTemplate`** — зарегистрированный шаблон: ID, название, текст/паттерн, имя отправителя, статус, дата регистрации, ежемесячная стоимость.
- **(AR) `AnalysisRun`** — прогон анализа по `batch_id + config_hash`: `TemplateMetrics[]` и `CandidateGroup[]`.
- `BillingRow` — строка-компонент внутри `SmsMessage`; собственной идентичности не имеет.
- `MessageClass` — `ORDINARY` / `TEMPLATED`.
- `Operator` — нормализованный оператор + исходное значение.
- `Money` — `Decimal` в RUB, квантование до копеек только на границе вывода.
- `segments` — количество SMS-сегментов, целое ≥ 0; правило 70/67 — в `count_segments`. Отдельный value object не вводим: одно поле без собственного поведения.
- `Period` — даты с часовым поясом; статистика приходит в `+03:00`.
- `TemplateMetrics` — активность, matched-сообщения, сегменты, стоимость, baseline, выгода, fee, net.
- `CandidateGroup` — группа незашаблонированных сообщений, сгенерированный шаблон, объём, выгода, уверенность.

### Инварианты

Инварианты проверяются корнем агрегата (`__post_init__`) или доменной фабрикой;
тест на инвариант обязателен. Внешние проверки (SQL, UI, адаптер) — дополнение,
не замена.

- `Money` не может быть `float`.
- Дата всегда timezone-aware.
- `segments >= 1` для отправленного сообщения; для ошибок допускается 0.
- Один `ID сообщения` = одно логическое сообщение; сумма стоимостей по биллинговым строкам.
- Стоимость не пересчитывается из текста, длины или прайса, если есть фактическая `Стоимость`.
- Отрицательная выгода допустима: неактивный шаблон стоит денег.

## 7. Тарифные модели

Три модели, реализуются через Strategy/Protocol:

1. `PackageTariff` — предоплаченный пакет SMS.
2. `SubscriptionTariff` — оплата блоками сообщений одному получателю.
3. `PayPerMessageTariff` — оплата по факту за обычные SMS.

Общие правила:

- Тариф выбирается по периоду, оператору и классу сообщения.
- Каталог тарифов — TOML с `effective_from` / `effective_to`. Не хардкодить ставки в коде.
- Для исторического периода сначала пытаться извлечь фактические ставки из статистики, затем брать каталог.
- `Стоимость` в статистике — фактическое списание. Для подписки она может быть 0 внутри блока; для пакета — стоимость списания из пакета.
- Пакет: цена за сегмент зависит от объёма пакета; поддерживать `uniform` и `marginal` режимы, проверять на фактических данных.
- Подписка: блоки считаются **на получателя**, а не на рассылку. Нужна симуляция последовательности сообщений по получателю за период.
- Шаблонный сбор: 2 000 ₽/мес за шаблон при подключённой подписке на шаблонированные SMS. Учитывать в выгоде.

Подробные ставки и алгоритмы — в skill `mts-sms-tariffs` и `.opencode/skills/mts-sms-tariffs/references/price-list-2026-11.md`.

## 8. Экономическая выгода

Базовая формула для шаблона:

```text
ordinary_rate = сумма стоимости обычных SMS периода / сумма их сегментов
baseline_cost = ordinary_rate × сегменты срабатываний

actual_cost   = сумма фактических списаний по срабатываниям
              + ежемесячная стоимость шаблона (2 000 ₽ × месяцы)

net_benefit   = baseline_cost - actual_cost
```

Формула для кандидата:

```text
templated_rate = сумма стоимости шаблонированных SMS периода / сумма их сегментов
templated_cost = templated_rate × сегменты группы

экономия периода = фактическая стоимость группы - templated_cost
monthly_saving   = экономия периода × monthly_factor
net_monthly      = monthly_saving - 2 000 ₽
```

Требования:

- Считать в `Decimal`, округлять только при выводе.
- Ставки `ordinary_rate` и `templated_rate` — средние по всем сообщениям класса с сегментами, включая нулевые списания внутри оплаченного блока. Это те же значения, что дашборд показывает в «Средняя стоимость сегмента».
- Для неактивного шаблона `baseline_cost = 0`, `net_benefit = -template_fee`; показывать «убыток от поддержания шаблона».
- Для кандидата (ещё не зарегистрированного) сравнивается фактически заплаченная сумма за период с оценкой по тарифу шаблонированных SMS; стоимость шаблона вычитается из месячной экономии. В UI и отчёте — колонки «Стоимость»/«Если шаблон» и «Стоимость/мес»/«Если шаблон/мес».
- Baseline по умолчанию — `observed`: средняя стоимость сегмента обычных SMS периода × сегменты срабатываний. Альтернатива — `catalog`: расчёт по каталогу тарифов на сообщение; включать как настройку.
- Если наблюдаемой ставки нет — `baseline = 0` и явное предупреждение; в отчёте методика помечается как оценка.
- В отчёте всегда показывать методику: observed vs catalog, период, ставки, fee.
- Цвет строки шаблона в UI определяется месячной выгодой `monthly_net_benefit` (той же моделью месяца, что у кандидата): пять зелёных уровней по порогам (по умолчанию 1 / 3 000 / 10 000 / 30 000 / 100 000 ₽), убыток — один слабо-красный уровень, ноль — без цвета. Пороги — настройка (`[benefit] thresholds`), а не константа в коде.
- Неполный период анализа (< 28 дней) моделируется до 30 дней: `monthly_factor = 30 / days`. Полный период не масштабируется. Модель применяется к выгоде кандидата и шаблона, к месячным объёмам/суммам в UI и отчёте; фактические суммы периода показываются отдельно (в UI — подсказкой ячейки, в отчёте — отдельными колонками). Для шаблона `monthly_net_benefit = (baseline_cost − actual_cost) × monthly_factor − template_fee`; `monthly_messages`/`monthly_segments` масштабируются с округлением половины вверх.
- Изменение формулы требует повышения версии в `compute_config_hash` (`benefit_formula`), иначе кэш вернёт устаревшие суммы.

## 9. Импорт данных

### Статистика МТС-Маркетолог

- Один лист, шапка в строке 1, 25 колонок. Точный список — в skill `mts-statistics-import`.
- Обязательные колонки: ID сообщения, дата попытки, текст, оператор, статус отправки, статус доставки, цена за сегмент, стоимость, количество сегментов, тип пакета, номер получателя, имя отправителя.
- Читать потоково/через `polars`, не грузить 100k строк в UI.
- Нормализовать заголовки: trim, BOM, пробелы, регистр.
- Даты — ISO с `+03:00`; деньги — `Decimal`; пустые строки — `None`.
- Дедупликация по `ID сообщения` с суммированием стоимости и сегментов: длинная SMS разбита на несколько оплачиваемых частей.
- Статусы отправки и доставки сохраняются в `SmsMessage.send_status` / `delivery_status` (первое непустое значение среди биллинговых строк) и пишутся в SQLite; производный `delivered` остаётся для фильтров.
- Ошибки импорта — атомарно: либо весь файл, либо откат.
- Хранить SHA-256 файла и параметры импорта; повторный импорт того же файла должен быть идемпотентным.
- Показывать пользователю отчёт: строк, уникальных сообщений, период, ошибки, дубликаты, сумму, предупреждения.

### Список шаблонов

Источник — реальная выгрузка «Список шаблонов.xlsx» из личного кабинета МТС-Маркетолога. Правила синтаксиса — раздел 9.1.

Колонки выгрузки:

| Колонка | Обязательна | Назначение |
|---|---|---|
| `ID шаблона` | нет | идентификатор регистрации; становится `template_id` |
| `Текст шаблона` | да | текст в синтаксисе МТС; ключ сопоставления |
| `Текст (пример) шаблона` | нет | пример, обязан проходить шаблон |
| `Имя отправителя` | нет | отправитель; пустой — шаблон универсальный |
| `Статус` | нет | `Подключен` / `Отключен` |
| `Операторы` | нет | операторы регистрации через `/`, `,` или `;` |

Требования к адаптеру:

- Колонки сопоставляются по заголовкам и через диалог. Дополнительно поддерживаются `Название`, `Стоимость`, `Тип трафика`; служебные колонки (`Юридическое лицо`, `ИНН`, `Комментарий Стрим`) не используются.
- Если статуса нет — шаблон считается подключённым. Неизвестный статус — отключён, с предупреждением.
- Если стоимости нет — брать 2 000 ₽/мес из конфига.
- Строки, нарушающие правила составления (9.1), не импортируются; в отчёте — номер строки и причина.
- Пример из `Текст (пример) шаблона` обязан проходить шаблон; иначе — предупреждение, шаблон сохраняется.
- Валидировать пустые тексты, дубликаты ID, неизвестных операторов.

#### Один шаблон на нескольких операторов

Выгрузка представляет шаблон, зарегистрированный на нескольких операторов, двумя способами:

1. **Компактный** — одна запись, в `Операторы` перечислены все операторы: `МТС/билайн/МегаФон/Ростелеком`.
2. **Развёрнутый** — несколько записей с разными `ID шаблона`, в каждой один оператор или неполный список: `13549` → `МТС`, `13559` → `билайн`.

Правила объединения:

- Ключ тождества шаблона — `(Имя отправителя, текст шаблона)`; текст сравнивается посимвольно, включая регистр, пунктуацию и пробелы. Две записи с одинаковым ключом — один шаблон. Это правило импорта; при сопоставлении сообщения с шаблоном действуют правила 9.1 (регистр и пунктуация не учитываются).
- `operators` шаблона — объединение операторов подключённых записей; пустое множество — «все операторы».
- Запись со статусом `Отключен` не добавляет оператора: шаблон для него не применяется. Если шаблон подключён хотя бы одной записью — он активен; операторы отключённых записей выводятся в предупреждении.
- Если отключены все записи — шаблон неактивен.
- `template_id` — минимальный числовой `ID шаблона` среди объединённых записей (устойчив к повторному импорту).
- **Плата за шаблон взимается один раз**, независимо от числа записей и операторов. Поэтому объединение обязательно до расчёта выгоды.
- Импорт заменяет набор шаблонов: записи, которых нет в новой выгрузке, удаляются, кэш прогонов анализа сбрасывается.
- В отчёт импорта выводится: записей в файле, шаблонов после объединения, удалено, предупреждения по строкам.
- Тождество шаблона — только точный текст. Варианты с постоянным окончанием (например, `… — DOCTORLIGHT` для Tele2) и без него — **разные** шаблоны: они не сливаются ни при импорте, ни в таблице. В UI шаблон идентифицируется колонкой «Шаблон» с полным текстом, а не обрезанным `name`: обрезка до 60 символов делала такие пары визуально одинаковыми.

### 9.1 Правила составления и применения шаблона МТС

Основа — «Порядок согласования шаблонов МТС» (support.mts.ru, обновлено 07.10.2026) и примеры из файла шаблонов. Приложение **применяет** эти правила при сопоставлении; оно не угадывает шаблон по похожести.

Переменные части:

| Запись | Смысл | Соответствие в тексте SMS |
|---|---|---|
| `%w` | одно слово: непрерывный набор букв, цифр, спецсимволов без пробела | ровно один токен без пробелов |
| `%w{1,n}` | от 1 до n слов через пробел, `n ≤ 20` | 1..n токенов без пробелов |
| `%d` | одно числовое значение: цифры и спецсимволы без пробела (дата, время, сумма, код) | один токен из цифр |
| `%d+` | одна или несколько числовых групп через пробел | `\d+(?:\s+\d+)*` |
| `%d{1,n}` | от 1 до n числовых групп | `\d+(?:\s+\d+){0,n-1}` |

Запрещено в шаблоне:

- `%w+` (любой набор без ограничения) и `%w{1,1}`, `%d{1,1}` — писать `%w` и `%d`;
- подряд идущие групповые переменные (`%w{1,n} %d+`, `%d+ %w{1,n}`, `%w{1,n} %w{1,m}` и т. п.);
- неизвестные конструкции `%x`, символы `|,|.`;
- шаблон без постоянного текста или с текстом вне кириллицы и латиницы.

Правила сравнения, выведенные из примеров:

1. При **сопоставлении сообщения с шаблоном** знаки препинания и лишние пробелы не учитываются (правило 5.15.1: при загрузке удаляются из текста шаблона). Регистр не учитывается. Пример: `%w{1,3} Ваши результаты готовы.` соответствует `Казакова З Р, Ваши результаты готовы.` с `%w{1,3}` = «Казакова З Р». Тождество записей выгрузки (раздел 9) определяется иначе — по точному тексту.
2. Дата и время (`12.08.2026 17:40`) — два `%d`. `2026-08-03` и `711-100, 255-100.` — `%d` и `%d+`.
3. Постоянная часть шаблона должна совпасть полностью. Частичное совпадение не считается.
4. Переменная может быть отдельным словом или стоять рядом с пунктуацией: `(%w часов голода)`.
5. Шаблон **применим** к SMS, если имя отправителя совпадает с `Имя отправителя` и текст проходит грамматику шаблона. Оператор получателя на применимость не влияет: он определяет, оплатит ли МТС сообщение по тарифу шаблонированных SMS.
6. Оператор получателя входит в список `Операторы` шаблона — условие корректной тарификации, а не подпадания под шаблон. Если оператор определён неверно, сообщение тарифицируется как обычное; это выявляет процент срабатывания.
7. Пример из колонки `Текст (пример) шаблона` обязан проходить шаблон. Несоответствие — предупреждение импорта, шаблон сохраняется.
8. Пустой список операторов означает «все операторы» — с предупреждением при импорте.

Генерация шаблона-кандидата (раздел 11) выдаёт текст в том же синтаксисе: числа, даты, суммы, время → `%d`; ссылки, e-mail, телефоны → `%w`; постоянные слова остаются литералами. Группы `%w{1,n}` автоматически не выводятся: кандидат проверяется человеком перед регистрацией.

## 10. Анализ шаблонов

- Сопоставление — только по грамматике раздела 9.1, без fuzzy. Сообщение, которое не проходит грамматику, не относится к шаблону.
- **Подпадание под шаблон**: совпали имя отправителя и текст по грамматике. Оператор получателя на подпадание не влияет.
- Один шаблон на сообщение: сначала отбираются шаблоны с подходящим отправителем; при нескольких — более длинная постоянная часть, затем меньше переменных. Если шаблоны покрывают текст одинаково (тексты различаются только регистром, пунктуацией или пробелами), выбирается тот, в списке `Операторы` которого есть получатель; иначе — первый по `template_id`.
- Активность: есть хотя бы одно отправленное сообщение (не ошибка отправки), подпавшее под шаблон. Доставку показывать отдельно.
- **Срабатывание** = сообщение подпало под шаблон **и** оплачено по тарифу шаблонированных SMS (`MessageClass.TEMPLATED`).
- **Процент срабатывания** = `triggered_messages / matched_messages`, где `matched_messages` — все сообщения, подпавшие под шаблон за период. Метрика подписывается «Срабатывание, %».
- Причина срабатывания ниже 100 % — оператор получателя не входит в список `Операторы` шаблона (шаблоны регистрируются под требования конкретных операторов) либо оператор абонента определён неверно. Поэтому процент срабатывания считается и в разбивке по операторам получателя: `(шаблон, оператор) → подпало / сработало / сегментов подпало`.
- Доля сегментов оператора в шаблоне = `matched_segments оператора / сумма matched_segments по шаблону`.
- Стоимость и baseline шаблона считаются только по срабатываниям. Baseline = средняя стоимость сегмента обычных SMS периода × сегменты срабатываний. Сообщения, подпавшие под шаблон, но оплаченные как обычные, в экономику не входят; их общее число и число «оператор вне списка» выводятся в предупреждениях и в разбивке по операторам.
- Непривязанные шаблонированные сообщения (оплачены как шаблонные, но ни один шаблон не подошёл) — отдельное предупреждение: вероятно, не зарегистрирован шаблон или не совпал отправитель/текст.
- Для неактивных шаблонов искать близкие незашаблонированные сообщения и предлагать удалить/скорректировать.
- Все метрики — за выбранный период, с указанием периода и фильтров.
- Средняя длина сообщения в сегментах = `segments / messages`; средняя стоимость = `cost / messages`. Доли обычных и шаблонированных считаются от общего количества сообщений.

## 11. Поиск кандидатов (MTS-CSG)

Детерминированная сигнатурная группировка, без статистических методов.
Пайплайн (`domain/analytics/`: `normalization.py`, `canonical.py`, `csg.py`):

1. Отфильтровать доставленные, не сопоставленные с шаблонами сообщения с непустым текстом.
2. Нормализовать по общей политике (раздел 11.1).
3. Токенизировать: литеральные слова, числовые серии, raw-сущности (URL, e-mail, телефоны, токены с цифрами и буквами) — переменные-слова.
4. Каноническая сигнатура: литералы — по значениям, числа — только по числу групп в серии, переменные — маркером.
5. Точная группировка по `(отправитель, сигнатура)`.
6. Эмиссия шаблона: числа → `%d`/`%d{1,n}`/`%d+` по наблюдаемым длинам серий, переменные → `%w`, литералы — в исходной форме сообщений (`Token.surface`): регистр, пунктуация и тире сохраняются (`Заказ %d — готов, заберите в пункте «Выдача»!`). Если в группе разные написания литерала, берётся самое частое, при равенстве — первое по алфавиту; поверхность с `%` или `|` отбрасывается.
7. Слияние литеральных участков в `%w`/`%w{1,n}` (только для подтверждения человеком): по «скелету» сигнатуры с сохранением общего префикса, суффикса и якоря внутри участка; хвостовые варианты (`… паспорт` и `… паспорт DOCTORLIGHT`) остаются разными шаблонами; одиночный участок с числом вариантов ≤ `max_literal_cardinality` не обобщается.
8. Линтер (правила 9.1, плюс две словесные переменные подряд запрещены) → проверка полным совпадением (`fullmatch`) всех сообщений группы → защита от чужих совпадений (`max_foreign_matches`).
9. Отсортировать по объёму; экспорт в Excel; регистрация — только после подтверждения человеком.

Правила отбора и прогноза:

- Порог группы — минимум сообщений (`min_support`) и минимум SMS-сегментов (`min_cluster_segments`): итоговая выгода шаблона зависит от числа сегментов.
- Статусы кандидата: `auto_validated` (точная группа, прошла все проверки), `needs_human_approval` (есть предложенная `%w{1,n}`), `warning_saved` (отправители объединены без учёта регистра), `rejected` (отклонён линтером/полнотой/чужими совпадениями).
- Группы, которые шаблон покрывает целиком, считаются «поглощёнными»: их сообщения входят в кандидата, а не в чужие совпадения.
- Для неполного периода (< 28 дней) экономическая выгода моделируется до целого месяца: `monthly_factor = 30 / days`; в UI и отчёте месячные объёмы, фактическая стоимость и оценка по шаблону показываются отдельно от фактических за период.
- Экономия периода = фактическая стоимость группы − `templated_cost`; `templated_cost` = средняя стоимость сегмента шаблонированных SMS × сегменты группы. Стоимость шаблона вычитается из месячной экономии.
- Окупаемость считается от смоделированной месячной экономии и ежемесячной стоимости шаблона.

Запрещено:

- автоматически регистрировать шаблоны без подтверждения;
- использовать как решающий механизм TF-IDF/cosine, embeddings, DBSCAN/HDBSCAN, Levenshtein/fuzzy, Drain/Spell, лемматизацию;
- скрывать низкую уверенность объединения.

### 11.1 Нормализация текста

Общая политика (`NormalizationPolicy`) едина для поиска кандидатов, грамматики шаблонов и матчинга:

- Unicode NFKC, схлопывание пробелов, унификация кавычек и тире, нижний регистр;
- нормализация нужна только для сравнения: группировка и матчинг регистр и пунктуацию не учитывают, а текст шаблона-кандидата собирается из исходной формы литералов (`surface`) и сохраняет регистр, знаки препинания и тире;
- пунктуация: `delete` (по умолчанию) / `space` / `keep`;
- свёртка `ё → е` и омоглифов — только по настройке (`fold_yo`, `fold_homoglyphs`), по умолчанию выключена;
- имя отправителя сравнивается без учёта регистра, если не включён `sender_case_sensitive`.

## 12. Десктопный интерфейс

- PySide6, отдельный слой `presentation`.

- Деньги и даты форматировать в UI, не в домене.
- Русские подписи и сообщения об ошибках; код и идентификаторы — английские.
- Настройки: период, модель baseline, параметры поиска кандидатов, минимум сообщений и сегментов в группе, пороги выгоды, путь к данным, стоимость шаблона.

Цвет вычисляется в presentation по порогам из настроек; изменение настроек перерисовывает обе таблицы без пересчёта анализа. В таблице шаблонов колонка «Шаблон» забирает свободное место, остальные колонки подгоняются по содержимому; в таблице кандидатов так же, колонки «Окупаемость» нет — выгоду полностью определяет «Выгода/мес». - Таблица шаблонов: колонка «Шаблон» показывает полный текст шаблона (подсказка — текст целиком и подсказка открыть сообщения), сразу за ней — «Операторы» (компактные короткие имена, пустой список — «все»). Колонка «Отправитель» — последняя. Узкие колонки «Сообщений» (50 px), «Достав.» (57 px), «Срабат.» (67 px) и «% Срабат.» (60 px) в 1,5 раза уже обычных и не разрастаются при подгоне ширин. Колонки «% от всех» и «% от шабл.» — доля сегментов сообщений, подпавших под шаблон, во всех сегментах сообщений периода и в сегментах шаблонированных SMS периода; это доли за период, а не месячная модель (`TemplateMetricsView.share_of_all_segments` / `share_of_templated_segments`, знаменатели — `AnalysisView.total_segments` / `templated_segments`). В таблице операторов колонка называется «Сообщений». Клик по тексту шаблона-кандидата открывает окно его сообщений, где вверху есть полный текст и кнопка копирования. Суммы экономии выводятся rich-текстом (`_benefit_hint_html`): цвет `positive` активной темы (в системной — зелёный `#1b7f3a`), 15 px, полужирный; та же расшифровка без разметки (`_benefit_tooltip`) — в подсказке карточки. Шаблонированные SMS в них окрашены «морской волной» (`TEMPLATED_CHART_COLOR = #0d9488`), обычные — цветом `negative` активной темы: чистый зелёный оставлен за корпоративным цветом МегаФона в диаграммах операторов. Столбец дня составлен снизу вверх по убыванию массовости оператора за этот день; цвета — те же, что в круговых диаграммах (`operator_color`). Легенда — по суммарной массовости за период; подпись — «всего N сегментов». Данные готовит Qt-free `presentation/desktop/daily_chart.py` (`build_daily_chart`, `nice_scale`). - Блок «Дополнительно» (после «Основного», перед предупреждениями): карточки «Уникальных абонентов» (подпись — число операторов), «Сегментов на абонента» и «Сообщений на абонента» (средние по абонентам), затем три диаграммы в один ряд: гистограмма абонентов по числу сегментов, круговая диаграмма абонентов по операторам (топ-5, «Другие»), гистограмма сообщений по числу сегментов. Гистограммы — `DistributionChart` на `QPainter`: сегменты 1–9 — отдельными столбцами (нули показываются), дальше — диапазоны `10–19`, `20–49`, `50–99`, `100+`; у каждого столбца — количество и доля. Точные столбцы рисуются градиентом, задаваемым при создании (`exact_gradient`): у гистограммы сообщений он тёмно-горчичный (`DARK_MUSTARD_GRADIENT`), у абонентов — синий по умолчанию. Группировка — `presentation/desktop/distribution.py` (без Qt). Данные — `MessageQueryRepository.segmentation_statistics`, в SQL: абонент — `COUNT(DISTINCT recipient)` по сообщениям с `segments > 0`; сегменты абонента — сумма по его сообщениям; оператор абонента — по наибольшему числу сообщений (`ROW_NUMBER`), чтобы сумма по операторам совпадала с числом абонентов. Под блоком — пояснение о допущениях.

Доля — от общего количества сообщений загрузки; агрегаты — `MessageQueryRepository.operator_statistics`.
- Таблица «Срабатывание по операторам получателя» показывает только строки шаблона, выделенного в основной таблице; при смене выделения, фильтра или загрузки она пересобирается. Если ничего не выделено — таблица пуста, а заголовок не содержит имени шаблона. Колонки: оператор, «В списке», «Подпало», «Сегментов», «Доля (%)», «Срабатываний», «Срабатывание»; доля — сегменты «Подпало» оператора ко всем сегментам «Подпало» шаблона.

Карточка (`widgets/theme_card.py`) рисует миниатюру интерфейса в стиле темы, название и радиокнопку; выбранная выделена акцентной рамкой и галочкой, наведение анимирует подсветку (`QPropertyAnimation`). Каталог тем — `presentation/desktop/theme_catalog.py` (палитры и QSS, без Qt), применение — `theme.py` (`apply_theme`, `active_palette`), системная тема — пустой QSS. ## 14. Качество и тесты

Обязательные тесты:

- `Money`: Decimal, округление, отрицательные значения.
- Сегментация SMS: 70/71 символ, 67-символьные сегменты.
- Пакетный тариф: границы tier'ов, `uniform`/`marginal`, overage, ограничения пакета.
- Подписочный тариф: 1-е, 5-е, 6-е, 20-е, 21-е, 22-е сообщение одному получателю; обычные и шаблонные правила; сброс по месяцу.
- Шаблонный fee: 1 шаблон, несколько, неполный месяц, повторное подключение.
- Выгода: активный, неактивный, нулевая, отрицательная, округление.
- Дедупликация: несколько биллинговых строк, разные стоимости, несовпадение метаданных.
- Инварианты агрегатов: `SmsMessage` (стоимость, сегменты, дата), `SmsTemplate` (текст, fee), `AnalysisRun` (ключ `batch_id + config_hash`).
- Матчинг по правилам 9.1: постоянный текст, переменные `%w`/`%w{1,n}`/`%d`/`%d+`, отправитель; независимость подпадания от оператора; запрещённые конструкции отклоняются; несколько шаблонов — приоритет по специфичности.
- Срабатывание: `trigger_rate = triggered / matched`; сообщение подпало, но оплачено как обычное — не входит в экономику; разбивка `(шаблон, оператор)` показывает оператора вне списка шаблона.
- Сигнатурная группировка (`test_csg.py`): нормализация и политика, канонические сигнатуры, raw-сущности, линтер, слияние (cardinality ≤ 3 не обобщается, якорь сохраняется, хвост `… паспорт`/`… паспорт DOCTORLIGHT` — разные шаблоны), анти-оверматч, поглощение групп, статусы кандидатов, полный `fullmatch`, регистр отправителя.
- Выгода в UI: уровни цвета по порогам (границы 1 / 3 000 / 10 000 / 30 000 / 100 000 ₽), убыток, ноль; настраиваемые пороги валидируются по возрастанию.
- Отображение таблиц: булево значение — галочка/крестик; разбивка по операторам фильтруется по выделенному шаблону (`operator_rows_for_template`); строка кандидата красится по `net_monthly` теми же порогами, что и шаблон.
- Абоненты и распределения: абонент — уникальный получатель с сегментами > 0; сегменты абонента — сумма по его сообщениям; оператор абонента — по большинству сообщений, ничья — по алфавиту; сумма по операторам равна числу абонентов; сообщения с 0 сегментов не входят в распределения; группировка 1–9 / 10–19 / 20–49 / 50–99 / 100+ сохраняет количество и долю (`test_distribution.py`).
- Дневные серии: `TemplateActivity` копит подпавшие под шаблон сегменты по дням, `CandidateGroup.daily_segments` — сегменты сообщений кандидата, `AnalysisRun.daily_segments` — весь трафик дня; дубликаты дат и превышение трафика дня отклоняются, сумма дневных сегментов кандидата обязана совпадать с его `segments`; прогон сохраняет и загружает все ряды через payload; `build_segment_daily_chart` заполняет дни периода, кладёт базовый трафик дня teal, совпавшие сегменты dark orange накладкой от общей базовой высоты, считает подпись и легенду по `series_label`/`matched_label`; `templated_only` переключает базу на шаблонированный трафик; `merge_day_segments` складывает ряды по датам; `overlay_geometry` не даёт накладке выйти за верх столбца и держит минимальную видимую высоту.
- Дашборд: средние и доли считаются по сегментам, `delivered_share` не делит на ноль; карточки и блок «Основное» заполняются из `BatchStatistics`; таблица операторов — из `operator_statistics` (убывание сообщений, доля от всех сообщений).
- Наблюдаемые ставки: средние по классам включают нулевые списания и недоставленные сегменты; `OperatorTrigger` несёт `matched_segments`, доля оператора = сегменты подпало оператора / сегменты подпало шаблона.
- Месячная модель: полный период не масштабируется, неполный — до 30 дней; средние и доли статистики не делят на ноль.
- Список сообщений: `resolve_template` учитывает универсальные шаблоны с пустым отправителем, `matches_candidate_pattern` — отправитель и полный `fullmatch`, `is_candidate_message` — класс/сегменты/доставку; `for_template` и `for_candidate` возвращают реальные сообщения загрузки с замаскированным номером и статусом доставки; колонки окна не показывают полный номер.
- Интеграция: импорт маленького XLSX в temp SQLite → анализ → отчёт.

Правила:

- Фикстуры — маленькие (10–100 строк), руки не тянуть к реальным выгрузкам.
- Для реальных данных — только ручная проверка через `.opencode/skills/mts-statistics-import/scripts/profile_statistics.py`; результаты не коммитить.
- Перед завершением задачи: `ruff`, `mypy`, `pytest`. Если что-то не запускается — указать явно.
- Не утверждать «работает», если не запускал проверки.

## 17. Открытые вопросы и допущения

До получения ответов используем указанные допущения и явно показываем их в UI/отчёте:

1. **Формат Excel со списком шаблонов** — получена реальная выгрузка `doc/Список шаблонов.xlsx`: `ID шаблона`, `Текст шаблона`, `Текст (пример) шаблона`, `Имя отправителя`, `Статус`, `Операторы`. Записи одного шаблона у разных операторов объединяются по отправителю и **точному** тексту: регистр, пунктуация и пробелы значимы (раздел 9). Полной выгрузки пока нет — будет позже.
2. **«Процент срабатывания»** — подтверждено заказчиком: `triggered_messages / matched_messages`, где числитель — подпавшие под шаблон и оплаченные по тарифу шаблонированных SMS, знаменатель — все сообщения, подпавшие под шаблон (раздел 10). Снижение ниже 100 % объясняется оператором получателя вне списка шаблона или неверным определением оператора; поэтому метрика выводится и в разбивке по операторам.
3. **Baseline для выгоды** — подтверждено заказчиком методикой от 17.11.2026: средняя стоимость сегмента обычных SMS периода × сегменты срабатываний (observed). Альтернатива — расчёт по каталогу тарифов (catalog). Для кандидата экономия = фактическая стоимость группы − средняя стоимость сегмента шаблонированных SMS × сегменты группы, стоимость шаблона вычитается из месячной экономии.
4. **Стоимость шаблона**: 2 000 ₽/мес за шаблон при подключённой подписке на шаблонированные SMS (из `prices.pdf`). Если у заказчика другая ставка — вынести в настройки.
5. **Дубликаты ID**: трактуем как биллинговые компоненты, суммируем стоимость, сообщение считаем один раз. Требуется подтверждение заказчика.
6. **Ноябрь неполный**: сравнения с октябрём показывать с предупреждением; при необходимости нормализовать на день.
7. **«СМС» в ТЗ**: различаем «сообщение» (логическая отправка) и «SMS-сегмент» (биллинговая единица). В отчётах подписываем явно.
8. **Экспорт**: Excel — основной; CSV — дополнительно. Формат отчёта согласовать после первого прототипа.

## 19. Definition of Done

Задача считается выполненной, когда:

- Изменения соответствуют слоям и не нарушают направление зависимостей.
- Новая бизнес-логика находится в домене и названа по единому языку (раздел 5.2).
- Инварианты агрегатов проверяются в модели и покрыты тестами на границах.
- Бизнес-логика покрыта unit-тестами; интеграционный сценарий — хотя бы один.
- `ruff`, `mypy`, `pytest` проходят (или явно указано, что не запускалось и почему).
- На реальной выгрузке проверены: количество строк, уникальных сообщений, дубликаты, сумма, ошибки, период.
- В UI/отчёте видны период, методика расчёта и предупреждения о допущениях.
- Персональные данные не попали в логи, тесты и репозиторий.
- Обновлены `AGENTS.md` и/или соответствующий skill, если изменились правила или формат данных.
